# Inputs to the deferred evaluator design decision

The user authorized completing the compact fix and full validation, while
reserving judgment on whether to rewrite the evaluation layer. No rewrite
is authorized or chosen by this record. The user subsequently authorized the
bounded [data-layer plan](data-layer-plan.md): executable metadata plus ordinary
proofs of correspondence, with ordinary lemmas/explicit witnesses for individual
judgments and no computational proofs. General solver redesign stays deferred.

## What the current implementation establishes

- A uniform, proved compact enumeration over the existing occupation subtype,
  with no source-word enumeration or executed count-vector deduplication.
- Explicit opt-in decisions for the unchanged structural predicates.
- Actual original Q18 allowance and a neutral mixed-content prohibition,
  kernel-checked under the unchanged 6 GiB closed-probe ceiling.
- Focused builds, strict transitive audits, rejection controls and a complete
  default-root build under the explicitly authorized 10 GiB full-build guard.

These are useful stable interfaces even if the evaluation engine changes later.
The original all-degree support theorem and coefficient-space semantics do not
need to be replaced merely because their proof-bearing syntax is inconvenient
for execution.

## Subsequent remaining checks

The user later authorized consuming the remaining checks under a 10 GiB guard.
[Final results](remaining-checks-results.md) prove all 107 fixed-domain signs
by independent kernel certificates with existing filters and explicit witnesses
(41 positive, 66 zero; 334 strict checks; 26.0 s; about 5.37 GiB). The naive
path completed 30 rows with 9 matches and 21 memory interruptions before the
comparison moved to certificates. Raw unattempted keys remain explicitly
unbenchmarked. General compiled execution still fails on noncomputable inputs.
The larger mixed negative is provable by the existing parity theorem even though
the raw decision hit the memory guard. This narrows what a rewrite would need
to address; it does not choose a design.

The user also included the [572-assignment reassessment](assignment-results.md).
All rows are now kernel-checked: 326 B1/B2 allowed, 144 B1 forbidden/B2 allowed,
102 both forbidden; no unknown cases. The 1716 assignment theorems and 3724
strict checks pass in 87.9 s at about 6.62 GiB. Symbolic parity/charge exclusion
and 23 explicit joint witness families suffice for this finite consumer.
This supports using proved filters and witnesses for a defined request; it
does not establish general raw-enumeration scalability or choose a rewrite.

## Executable data-layer extension: resource stop

The subsequent authorized [implementation](data-layer-results.md) verifies
executable mathematical core metadata and generic generation/species
composition with ordinary correspondence proofs. No new computational support
proof is used. The complete SM bridge candidate hit the 10 GiB sampled guard
at 60.1 s/10508652 KiB (about 10.02 GiB); development stopped there. The run
has no declaration-level progress diagnostic, so the particular allocation
bottleneck is not isolated. The unverified candidate is stored outside active
sources; SM support equivalence and new mixed proof consumers remain pending.
This is a verified partial result plus a resource boundary, not completion of
the data-layer plan or evidence for a compiler optimization defect.

The user then authorized a bounded connection revision. The
[verified revision](data-connection-results.md) avoids the old dependent
projection comparison and transports through the same actual joint source.
Full SM support/Higgs/original-space equivalence and ordinary mixed/Q18/negative
consumers now pass. Fresh downstream applications are checked within the
10 GiB/120-second guard. This resolves the data-connection stop; general
witness search and compiled decision-engine scalability remain separate.

## What this does not establish

The decisions still depend on noncomputable presentation metadata for compiled
execution. No general `#eval` support solver, executable all-content API,
complete raw 107-row benchmark has been delivered. The original negative
mixed example is small; positive Q18 can short-circuit. Neither measures the
worst case of exhaustive occupation/component/color/path rejection. Color
permutation enumeration remains factorial in the number of flags.

The complete build's sampled peak of about 6.41 GiB measures repository-wide
checking including pre-existing modules, not isolated evaluator runtime. It
cannot by itself diagnose the new evaluator's memory requirements or establish
that a rewrite is necessary. The 6 GiB original full-build failure and successful
10 GiB rerun were external guards, not changes to kernel trust or proof limits.

## Possible later scope

If the user chooses a rewrite, freeze it around an executable metadata/decision
layer with a proved bridge to the existing predicates. Preserve the compact
occupation equivalence and original-space theorem as semantic interfaces.
Assess it with neutral negative cases whose charge filters pass and a precisely
defined finite benchmark domain, alongside positive controls. Reachable-spin DP
and complete owner-level matching are possible components, not existing proved
replacements here. Do not import numerical/CSV answers as theorem premises.

If the user retains the present path, the next investigation should measure a
bounded set of more demanding negative cases before claiming scalability.
Neither option is started by completion of this topic. Literature-documentation
consistency fixes, master integration and remote publication remain separate.
